# 01 — هيكلة المشروع

القاعدة الحاكمة: **ملفات المشروع لا تصير سباغيتي.**
لكل ملف موضع واحد متوقَّع، ولكل طبقة اتجاه اعتماد واحد.

---

## اتجاه الاعتماد — أحادي، لا يُعكَس

```
apps/e3ks_desktop  ─┐
                    ├──▶  packages/e3ks_engine  ──▶  (archive, xml فقط)
tools/e3ks_cli     ─┘
```

- المحرّك **لا يعرف** من يستدعيه. لا `import 'package:flutter/...'` فيه أبدًا.
- الواجهة **لا تحوي منطق تحويل**. لو كتبتَ في `apps/` سطرًا يفكّ ZIP أو يعدّل XML — فهو في المكان الخطأ.
- `tools/` و`apps/` لا يستوردان بعضهما.

## قاعدة الميزة (feature) في الواجهة

كل مجلد تحت `features/` مكتفٍ بذاته:

```
features/inspect/
├── inspect_screen.dart      ← الشاشة
├── inspect_controller.dart  ← الحالة والمنطق
└── widgets/                 ← ودجات هذه الميزة وحدها
```

- ودجة تستعملها ميزتان أو أكثر → تنتقل إلى `shared/widgets/`. **لا قبل ذلك.**
- ميزة تستورد من ميزة أخرى مباشرةً → إشارة إلى خطأ تصميم. المشترك يصعد إلى `shared/` أو ينزل إلى المحرّك.

## قواعد الملفات

- ملف واحد = مسؤولية واحدة. **تجاوز ٤٠٠ سطر يستدعي التقسيم.**
- اسم الملف `snake_case.dart` ويطابق ما يصدّره.
- ممنوع ملف باسم `utils.dart` أو `helpers.dart` أو `misc.dart` — هذه مقابر تُجمَع فيها الفوضى.
  سمِّ الملف بما يفعل: `hex_color.dart`، `zip_writer.dart`، `field_walker.dart`.
- كل ما هو عام يمرّ عبر `e3ks_engine.dart` وحده. لا استيراد من `src/` عبر الحزم.
- الملفات المؤقتة والمخرجات التجريبية **خارج شجرة المشروع**، لا تُترك بجوار الكود.

## القرارات المعمارية

كل قرار معماري له وزن يُسجَّل في `docs/adr/NNNN-عنوان.md`:
السياق ← القرار ← البدائل المرفوضة ← العواقب. مختصرًا، لكن مكتوبًا.
